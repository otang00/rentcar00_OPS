## 2. OPS 앱 전체 구현 상태

### 종합 판단
OPS 앱은 1차 운영 투입 가능한 수준까지 구현되어 있다.  
예약/차량/일정/직원/IMS/홈페이지 예약 수신까지 주요 운영 흐름은 대부분 들어가 있다.  
다만 실서비스 안정화 기준에서는 실기기 반복 검증, 미커밋 변경 정리, 가격 정책/홈페이지 동기화, 회계/정산 영역이 남아 있다.

### 완성도 추정
- 핵심 운영 MVP: 약 80~85%
- 실전 운영 안정화: 약 65~75%
- 장기 운영 시스템 완성도: 약 55~65%

위 수치는 코드/문서 기준 추정이다. 실제 직원 사용성, 현장 데이터 오류율, 다기기 동시 사용 검증까지 포함하면 낮아질 수 있다.

## 4. 빵빵카 홈페이지 관련 구현 상태

### 4-1. 홈페이지 자체 구현 완성도
현재 작업공간 기준으로는 확인 불가.

확인되지 않은 것:
- 홈페이지 소스 저장소
- 홈페이지 운영 URL/배포 플랫폼
- 실제 예약 폼 구현 코드
- 차량 목록/가격표/예약 확정 플로우
- 홈페이지 관리자 기능 유무
- 운영 결제/알림/문자/카카오 연동 여부
- 현재 실제 서비스 화면 기준 완성도

따라서 홈페이지 자체 완성도는 별도 접근 권한 또는 URL/저장소 확인 후 다시 평가해야 한다.

### 4-2. 홈페이지 → OPS 예약 이벤트 연동
구현 상태: OPS 수신부는 구현됨 / 홈페이지 송신부는 확인 필요

OPS 쪽 확인된 수신 endpoint:
```txt
POST /api/integrations/rentcar00/reservation-events
```

보안/중복 처리:
- `X-Rentcar00-Event-Type: reservation.created`
- `X-Rentcar00-Event-Id`
- `X-Rentcar00-Timestamp`
- `X-Rentcar00-Signature: sha256={hmacHex}`
- HMAC-SHA256 서명 검증
- timestamp 허용 오차 기본 5분
- 중복 eventId는 dedupe 처리

저장/생성 테이블:
- `rc00_ops_reservation_events`
- `rc00_ops_reservations`
- `rc00_ops_reservation_states`
- `rc00_ops_schedules`

생성 기준:
- `reservationInput` 우선 매핑
- 없으면 `booking` fallback
- `reservation_status = 예약중`
- `referral_source = 홈페이지`
- `check_payload_json.homepage_review = pending`
- `needs_attention = true`
- 배차/반납 일정 2건 자동 생성

OPS 앱 표시:
- 예약 목록 카드에 `홈페이지 확인` 배지
- 앱 상단 `홈페이지 N` 버튼
- 예약 상세에서 `홈페이지확인` 처리

남은 확인:
- 실제 홈페이지가 이 endpoint로 이벤트를 보내고 있는지
- 홈페이지 payload 필드명이 현재 parser의 `reservationInput` 매핑과 일치하는지
- 운영 secret이 홈페이지와 OPS parser 양쪽에 같은 값으로 설정되어 있는지
- 실제 예약 1건으로 end-to-end 검증했는지

### 4-3. 홈페이지 차량/가격 동기화
구현 상태: 확인 필요 / OPS repo에는 active 구현 기준 없음

현재 문서상 리스크:
- 홈페이지 차량 추가/동기화는 OPS repo 안에 현재 active 구현 기준이 없다.
- 자동차 그룹 기준이 불명확하면 앱/홈페이지/IMS 가격이 서로 다르게 적용될 수 있다.
- 가격 정책 수정은 예약 생성/수정, 홈페이지 이벤트, IMS import, 정산 후보 영역과 연결된다.

필요한 기준 정리:
1. 차량 기준 데이터의 원천이 어디인지
   - OPS DB
   - 홈페이지 DB/CMS
   - 별도 관리자
2. 가격 정책 원천이 어디인지
3. 홈페이지 예약 시점의 가격을 OPS에 어떤 필드로 넘기는지
4. 차량 그룹 변경 시 홈페이지/OPS/IMS 중 어디까지 영향을 주는지

## 6. 현재 리스크

### 높은 리스크
1. 홈페이지 실제 소스/배포 상태 미확인
   - 홈페이지 자체 완성도는 현재 문서만으로 판단 불가
2. 기존 미커밋 변경 존재
   - 현재 작업트리에 앱 UI/admin/pubspec 변경이 남아 있어 새 수정/배포에 섞일 수 있음
3. 가격 정책/차량 그룹 기준 미확정
   - OPS/홈페이지/IMS 간 가격 불일치 가능
4. 외부 연동 작업의 운영 영향
   - IMS 생성/변경/삭제, 홈페이지 이벤트 수신은 실제 운영 데이터에 영향

### 중간 리스크
1. Realtime은 네트워크/백그라운드 영향을 받음
2. 실기기 UI 확인이 일부 남아 있음
3. 작업로그는 적용 이후 액션부터 기록되며 과거 작업 retroactive 기록은 없음
4. 홈페이지 예약 payload 필드 변경 시 OPS 매핑 보정 필요

- 홈페이지 예약이 OPS 앱에서 `홈페이지 확인`으로 보이는지

### 3순위. 가격/차량 그룹 기준 잠금
- 차량 그룹 정의
- 가격 정책 원천
- OPS 예약 생성/수정 적용 범위
- 홈페이지 예약 이벤트 적용 범위
- IMS import와 가격 관계

### 4순위. 운영 안정화 체크리스트
- 직원 계정/권한 점검
- 실기기 2대 이상 realtime 확인
- 주요 예약 lifecycle 테스트
  - 홈페이지 예약 수신
  - OPS 예약 생성
  - IMS 등록
  - 차량변경
  - 배차완료
  - 반납완료
  - 예약취소
- GDrive APK 최신 1개 유지 확인

## 9. 결론

OPS 앱은 단순 목업이나 초기 개발 단계가 아니라, 실제 운영 투입을 전제로 대부분의 핵심 기능이 구현된 상태다.  
현재 가장 큰 빈칸은 앱 자체보다 `실제 서비스 중인 홈페이지의 소스/배포/예약 송신부 확인`과 `가격/차량 그룹 정책 확정`이다.

즉, 다음 개발 판단은 아래 순서가 안전하다.

1. OPS 앱 현재 미커밋 변경 정리
2. 예약 상세 누락 수정 + b50 APK 배포
3. 홈페이지 실제 구현 상태/예약 이벤트 송신부 확인
4. 차량/가격 정책을 OPS·홈페이지·IMS 공통 기준으로 잠금
5. 회계/정산은 별도 큰 phase로 분리

## 1. 이슈 요약

현장 직원이 누르는 `반납완료` 버튼은 단순히 차량을 다시 운영 가능 상태로 돌리는 버튼이어야 한다.
현재처럼 IMS 반납완료 필수 입력값까지 직원에게 요구하면 버튼 사용성이 떨어지고, 실제 현장에서 누르지 않을 가능성이 크다.

동시에 면허증 사진, 차량 사진 등록은 운영 기록과 분쟁 대응을 위해 슬슬 필요한 기능이다.
IMS Connect는 유류량, 주행거리 등 차량/계약 값을 내려받아 반납 입력 부담을 줄일 수 있는 후보로 본다.

## 2. 사장님 요청 기준

### 2.1 반납 버튼의 간편화

목표:
- OPS 반납 버튼을 자동화 또는 간소화한다.
- IMS 계약서를 권위 있는 기준 데이터로 둔다.
- OPS 버튼은 직원 업무를 최대한 줄이는 방향으로 설계한다.

원칙:
1. IMS 연결 예약정보가 없으면 OPS 반납완료를 바로 처리한다.
2. IMS 연결 예약정보가 있고 IMS에서 이미 `returned` 상태면, IMS 입력창 없이 OPS 반납완료를 처리한다.
3. IMS 연결 예약정보가 있으나 아직 IMS 반납 전이면, IMS 반납완료를 먼저 확인/처리한 뒤 OPS 반납완료를 진행한다.
4. 유류량/주행거리/유류비를 아무 값으로 자동 입력하는 방식은 정산/기록 오류 위험이 있어 기본안에서 제외한다.

### 2.2 면허증 사진 등록 및 차량 사진 등록

목표:
- 계약/배차/반납 업무에서 필요한 증빙 사진을 OPS에 남긴다.

필요 후보:
- 면허증 사진 등록
- 차량 외관 사진 등록
- 배차 전 사진 / 반납 후 사진 구분
- 예약 또는 계약 단위 첨부
- 파일 보관 위치와 개인정보 보호 기준 잠금

주의:
- 면허증 사진은 개인정보/민감정보에 가깝다.
- 저장 위치, 접근 권한, 삭제/보관 기간 기준을 먼저 잠가야 한다.
- 구현 전 별도 보안/운영 기준 PM이 필요하다.

### 2.3 IMS Connect 연결

목표:
- IMS Connect로 API 값을 내려받아 유류량, 키로수 등 반납 입력값 후보를 자동 채움 또는 확인값으로 사용한다.

활용 후보:
- 현재 유류량
- 현재/반납 주행거리
- 계약/차량 상태
- IMS 반납 여부
- IMS 계약서 PDF 또는 계약 상세 기준값

기대 효과:
- 직원이 직접 입력해야 하는 값 감소
- 반납완료 전 확인 단계 단순화
- 이미 IMS에서 반납된 예약은 OPS 처리만 남기는 흐름 가능

## 3. 최근 확인된 근거

확인된 IMS 조회 예시:
- IMS `scheduleId`: `4332133`
- 상태: `returned`
- 차량: `125하1717`
- 대여: `2026-07-03 13:58`
- 반납: `2026-07-07 15:13:53`
- 유류량: `16`
- 반납 주행거리: `29045`
- 유류비: 조회 응답에서 확인되지 않음

판단:
- IMS에서 이미 반납된 예약 여부는 조회로 확인 가능하다.
- 유류량/주행거리는 IMS 데이터에 남는 것으로 보인다.
- 유류비는 조회 응답에서 확인되지 않아 자동 임의 입력은 위험하다.

## 4. 권장 구현 방향 후보

### Phase 1. IMS 반납 상태 조회 게이트

목적:
- OPS 반납완료 전에 IMS 연결 여부와 IMS 반납 상태를 확인한다.

수정 후보:
- 중간서버 IMS 반납 상태 조회 API 추가
- 앱 반납완료 use case / repository 경로
- 일정 상세/예약 상세 반납완료 버튼 흐름

종료 조건:
- IMS 연결 없음: OPS 반납완료 바로 처리
- IMS 연결 있음 + IMS 상태 `returned`: IMS 입력창 없이 OPS 반납완료 처리
- IMS 연결 있음 + IMS 미반납: IMS 반납완료 선처리 안내

검증:
- IMS returned fixture/mock로 입력창 생략 확인
- IMS 미반납 fixture/mock로 선처리 안내 확인
- IMS 연결 없는 예약의 기존 OPS 반납완료 흐름 유지 확인

### Phase 2. IMS 반납 입력 자동 채움/확인 UX

목적:
- IMS 미반납 건에서 직원 입력 부담을 줄인다.

수정 후보:
- IMS Connect 또는 기존 IMS 상세 조회값 기반 유류량/주행거리 자동 채움
- 유류비 기본값/확인 정책 UI
- `0원 처리` 등 명시 확인 문구

종료 조건:
- 유류량/주행거리 후보값이 있으면 자동 채움된다.
- 유류비는 임의 확정하지 않고 직원 확인을 거친다.
- 확인 없이 가짜 값으로 IMS 반납완료를 호출하지 않는다.

검증:
- 후보값 있음/없음 케이스 UI 확인
- 유류비 미확인 상태에서 전송 차단 확인
- IMS 반납완료 성공 후 OPS 반납완료 연계 확인

### Phase 3. 면허증/차량 사진 등록 PM 분리

목적:
- 사진 등록 기능을 반납 버튼 개선과 섞지 않고 별도 보안/운영 기준으로 설계한다.

수정 후보:
- 예약/계약 단위 첨부 모델
- 면허증 사진, 배차 전 차량 사진, 반납 후 차량 사진 구분
- 저장소/접근권한/삭제정책
- 앱 촬영/업로드 UI

종료 조건:
- 어떤 사진을 어느 업무 단계에서 필수/선택으로 받을지 잠긴다.
- 개인정보 포함 파일의 저장 위치와 권한 기준이 문서화된다.
- 코드 구현 전 리스크와 롤백 기준이 정리된다.

검증:
- 샘플 예약 1건 기준 첨부 흐름 설계 리뷰
- 접근 권한/삭제 정책 체크리스트 통과

## 5. 리스크

- IMS API 응답 스키마가 차량/계약 유형별로 다를 수 있다.
- `returned` 상태 판단 기준을 잘못 잡으면 OPS와 IMS 상태가 벌어질 수 있다.
- 유류비를 자동으로 넣으면 정산 기록이 틀어질 수 있다.
- 면허증 사진은 개인정보 이슈가 크므로 저장/권한/보관기간 기준 없이 구현하면 위험하다.
- IMS Connect 연동은 외부 API 의존성이 커서 장애 시 OPS 반납완료가 막히지 않도록 fallback 기준이 필요하다.

## 6. 다음 결정 필요

2. IMS Connect를 바로 조사할지, 기존 IMS 조회 API로 먼저 최소 구현할지
3. 사진 등록은 별도 PM으로 분리할지
4. 면허증 사진 보관 정책을 어떤 기준으로 둘지

## 7. 현재 결론

우선순위는 `반납 버튼 간편화`가 가장 높다.
가장 안전한 1차 구현은 `IMS 상태 returned면 입력 없이 OPS 완료`, `미반납이면 IMS 반납 선처리` 흐름이다.
사진 등록과 IMS Connect 전체 연동은 별도 phase로 분리하는 것이 안전하다.
